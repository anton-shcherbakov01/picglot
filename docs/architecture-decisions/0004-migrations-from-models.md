# 4. The initial migration is materialised from the models

**Status:** accepted · 2026-08-02

## Context

Alembic's usual flow is `--autogenerate` against a live database. For the very
first revision of a fifty-table schema that produces a thousand-line file which
nobody reviews and which can silently disagree with the models it was generated
from.

## Decision

Revision `0001` calls `Base.metadata.create_all()` and then adds the Postgres-only
objects Alembic cannot infer: the `pg_trgm` extension, a trigram index on project
names, and partial indexes for the queue sweeper, the retention sweep and the
webhook retry scan.

Every subsequent revision is an ordinary autogenerated diff against this baseline.

## Consequences

- A fresh install cannot drift from the models — the schema _is_ the models.
- Ordinary migration workflow from revision 2 onward; nothing unusual to learn.
- `downgrade()` on revision 1 drops everything, which is correct for a baseline
  and is only ever used to reset a development database.
- The tests create the schema the same way (`create_all`), so the thing they
  exercise is the thing a fresh install gets.
